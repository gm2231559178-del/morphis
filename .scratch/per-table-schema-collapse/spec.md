# Spec: Per-table GraphQL generation collapse

Status: ready-for-agent
Priority: 4
Feature: per-table-schema-collapse

## Problem Statement

A single table's GraphQL surface — object type, relations, read queries, CRUD mutations, and filter inputs — is generated across five modules (`query`, `mutation`, `table`, `input`, `db`), orchestrated by a sixth (`mod`). The costs land on the developer who changes a table:

- Naming conventions are scattered string formats owned by different modules, and one concept ("the identity of a table") is keyed three different ways across the modules.
- `build_pk_args` exists verbatim in `query.rs` and `mutation.rs`; a PK-shape change is made twice.
- The three relation resolver variants (`has_many`, `has_one`, `belongs_to`) are near-copies differing only in which columns become `WHERE` clauses.
- The SQL dialect (`row_to_json` / `json_agg ... ORDER BY pk`) is re-typed in five places across the resolvers.
- The "run query, read JSON column, parse" DB idiom is copy-pasted four times in the db module.

## Solution

Collapse per-table generation into one deep module behind a single builder interface — `build_table_surface(config, table) -> object, query field, mutation fields, input types`. The module owns PK-arg building, relations, CRUD generation, filter inputs, and its SQL; the shared "query and parse JSON" helper folds in. The schema assembly module becomes a thin loop over the builder.

## User Stories

1. As a developer adding a column to a table, I want to touch one module, so that naming and scalar typing stay consistent in one place.
2. As a developer changing the primary-key shape of a table, I want to change it once, so that it cannot be updated in one file and missed in another.
3. As a developer adding a new relation type, I want one generator to extend, so that relation resolvers stop diverging.
4. As a developer fixing a SQL dialect bug (e.g. `row_to_json` / ordering inside `json_agg`), I want the dialect in one place, so that the fix lands everywhere at once.
5. As a developer, I want one construction path for a table's inputs and types, so that the naming-string formats live next to each other.
6. As a tester, I want the builder's interface to be the seam for schema-shape assertions, so that generated schema is unit-testable without the HTTP stack.
7. As a developer, I want the four near-identical DB-access functions reduced to one helper, so that binding/parse/error-mapping behaviour has one implementation.

## Implementation Decisions

- One builder: `build_table_surface(config, table_config) -> (Object, query field, mutation fields, input objects)`, called once per table by the schema assembly module.
- PK arguments built once inside the builder, used by both the read query and the CRUD mutations.
- Relation resolvers generated by one code path driven by the relation config (`has_many` / `has_one` / `belongs_to` differ in return shape and which columns feed the `WHERE`), sharing the FK → `WHERE` idiom and the related-table row-filter application.
- One private SQL helper owns the `row_to_json` / `json_agg ... ORDER BY pk` dialect used by queries, mutations, and relations.
- The db module's four functions collapse into one "run SQL, read JSON column" helper; error mapping (including the empty-result case that currently surfaces as a "no rows" error) is unified.
- The schema assembly module keeps its job of registering types and sequencing, but stops owning per-table naming decisions.
- No behaviour change to the generated schema: this is a locality refactor. Any type-name or field-name change visible to clients is a regression.

## Testing Decisions

- A good test asserts external behaviour: the generated schema is unchanged before/after; a table's query/mutation/relation surface behaves identically.
- Modules tested: the builder (new) through its interface — assert generated object/field/input names and shape; the existing resolvers through the hurl suite.
- Prior art: `circuit_breaker.rs` unit tests; `tests/queries.hurl`, `tests/mutations.hurl`, `tests/relations.hurl` for read/write/relation behaviour.
- New tests: schema-shape assertions on the builder (field names, input names, relation fields) matching the current naming conventions; the current `input.rs` re-implemented tests are replaced by tests of the real filter compiler once the typed-filter spec lands.
- Regression: the full hurl suite stays green; `tests/queries.hurl`'s introspection test is the guard against name drift.

## Out of Scope

- Typed numeric/null handling (separate spec: `typed-numeric-and-null-fields`) — it changes filter/write behaviour this refactor must preserve.
- The search module (separate spec: `search-module-deepening`) — the ES operator/row-filter internals stay where they are.
- Moving the schema assembly module's operator-input definitions into the search module.

## Further Notes

This is the locality payoff for the codebase's hottest surface — every future column, relation, or PK change touches one module instead of five. It is deliberately behaviour-neutral; its value is verified by the introspection test staying green and by the deletion of the duplicated `build_pk_args` and the four-way DB idiom. It should be sequenced after the typed-fields spec so it does not have to absorb behaviour changes mid-refactor.
